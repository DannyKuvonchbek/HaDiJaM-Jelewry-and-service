## Recorded implementation choices

The choices below are visible in code. Their rationale is inferred from implementation, not recovered from an unavailable discussion.

1. **Keep NestJS feature modules, Apollo code-first GraphQL, and MongoDB/Mongoose.** Evidence: `src/app.module.ts`, `src/database/database.module.ts`, feature modules. Inferred reason: reuse a consistent typed backend and domain separation. Risk: decorators and stored documents can diverge; schema generation requires bootstrapping. Alternative: schema-first contracts or a different persistence stack; no such switch is approved.
2. **Separate products and services; retain shared members/social infrastructure.** Evidence: product/service models and modules; like/view/comment group enums. Inferred reason: sales and service delivery have different lifecycles but share identities. Risk: a generic product is not automatically a pet/adoption record. Alternative: introduce explicit pet/adoption aggregates after requirements are known.
3. **Keep service bookings separate from salon reservations.** Evidence: separate models, modules, resolvers, collections. Inferred reason: appointments to provider services and suite reservations have different payloads. Risk: duplicate scheduling rules and confusing frontend flows. Alternative: unified resource scheduling or removal of the suite workflow if Petoria does not need it.
4. **Validate and price service bookings on the server.** Evidence: `service-booking.service.ts` resolves an active service, provider, price, technician, items and schedule. Inferred reason: prevent clients from choosing price/provider/status. Risk: jewelry rules and repair price 45 are hardcoded; text classification is fragile. Alternative: explicit service-kind enums, resource records, and configurable pricing/schedules.
5. **Use Seoul-local appointment rules.** Evidence: `Asia/Seoul` formatters and `+09:00` day boundaries. Inferred reason: consistent local slots. Risk: target regions and daylight-saving zones may differ; date/time input must agree. Alternative: provider time zones plus UTC timestamps and explicit date semantics.
6. **Enforce service booking uniqueness through a partial unique slot key.** Evidence: booking schema indexes and duplicate-key handling. Inferred reason: reject concurrent duplicates while allowing legacy missing fields; cancellation/rejection releases the key. Risk: index rollout may fail on duplicate existing data; service-scoped keys do not enforce global technician exclusivity. Alternative: atomic resource-slot records or transactional scheduling.
7. **Check salon availability in application code.** Evidence: `exists` before create/reschedule; nonunique compound index. Inferred reason: straightforward conflict feedback. Risk: check/write races permit duplicates. Alternative: unique active-slot key/index with atomic writes and explicit release on cancellation.
8. **Return viewer-specific like/follow metadata with list records.** Evidence: aggregation helpers in `src/libs/config.ts`, follows DTOs, product/service listing diffs. Inferred reason: avoid per-card requests. Risk: aggregation/index cost, nullable arrays, changed fragment type conditions. Alternative: separate batched relationship query or boolean computed fields with a versioned contract.
9. **Route follower counters through MemberService.** Evidence: changed follows service/module. Inferred reason: centralize member statistics updates and ObjectId handling. Risk: relationship writes and counter changes are separate operations and can drift on failure. Alternative: transactions or derived/reconciled counts.
10. **Use description-based jewelry catalog filters.** Evidence: product service regex synonyms and search DTO additions. Inferred reason: filter existing unstructured records without adding structured fields. Risk: imprecise matching and expensive regex scans; inappropriate for Petoria. Alternative: indexed structured target-domain attributes with backfill.
11. **Allow HEIC/HEIF uploads.** Evidence: `validMimeTypes` additions. Inferred reason: accept mobile-origin images. Risk: no verified conversion or client rendering path. Alternative: normalize images server-side or restrict accepted formats.
12. **Keep domain-specific human references.** Evidence: `HDJ-SVC-` and `HDJ-SAL-` generation. Inferred reason: user/support-friendly identifiers. Risk: legacy branding, truncation/collision handling, and external references. Alternative: new prefix for future records while preserving historical lookup.
13. **Use global DTO validation and development-only GraphQL introspection.** Evidence: bootstrap/app module. Inferred reason: consistent input handling and production exposure control. Risk: undeclared inputs are stripped; production schema discovery cannot be assumed. Alternative: publish a reviewed schema artifact for clients.

## Proposed migration decisions — not accepted or implemented

- Confirm that Petoria is a pet marketplace and define whether it sells goods, lists pets, supports adoption, or books care. The name alone cannot decide the data model. Risk: wrong aggregate design. Alternative: migrate branding only until product scope is explicit.
- Provisionally retain neutral `Product`, `Service`, `Member` contracts; change domain semantics only after client/data inventory. Reason: reduce unnecessary breaking changes. Risk: inherited fields remain misleading. Alternative: explicit versioned Petoria schema and adapters.
- Rename frontend GraphQL documents to reflect target features, but only call implemented backend root fields. Reason: client operation labels and schema fields are different. Risk: global replacement can break arguments, fragments, and cache keys. Alternative: temporary alias/adaptor layer after an actual old-schema audit.
- Preserve collections and ObjectIds initially; design idempotent data migration separately. Reason: current collections already support useful neutral concepts. Risk: legacy required fields and jewelry-specific data remain. Alternative: new collections plus verified reference remapping and rollback.
- Resolve suite reservation retention and account/provider role terminology before frontend booking implementation. Reason: the current salon model describes jewelry-client amenities. Risk: exposing irrelevant workflows. Alternative: a dedicated pet grooming/care model with pet/resource identity.
